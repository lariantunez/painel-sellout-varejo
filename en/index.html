00 · The challenge

Every month, the same spreadsheet, rebuilt from scratch.

The retail chain sends an export from its system with sales and inventory for every store and product. To answer sales leadership's questions, the analysis was built in Excel pivot tables: heavy files, one version per person, and the same manual work at every month-end close.

How much did we sell, in which store, in which category, and is inventory keeping up with sales? All of it without opening a spreadsheet.

01 · Principles

The front end displays. The backend processes. Mongo stores.

The architecture fits in one sentence, and four rules guided every decision:

01

The import is the most important part

All data comes in ready to query: numbers converted, dates standardized, category and family already stored. The dashboard never has to work anything out at display time.

02

Every import can be undone

Each row carries its batch ID. Undoing deletes exactly that batch, records it in the history and clears the cache.

03

No stale numbers on screen

Importing, undoing or clearing invalidates the cache. Correct data in Mongo behind an outdated dashboard is as serious an error as wrong data.

04

Role-based access

The primary user cannot be deleted or have their password changed through the dashboard. Admins manage users, and critical cleanups require the primary password.

04 · MongoDB model

One central collection, built to answer fast.

Sales and inventory data live in one central collection, dados_brutos. Each row of the file becomes a document, and the import adds prepared fields (prefixed with _) that queries use instead of the original fields.

Prepared fieldWhat it storesWhy it exists
_qtd_num · _valor_numUnits and value converted to numbersSum without parsing text on every query
_data_isoDate in YYYY-MM-DD formatFilter by period using an index
_gtinStandardized product codeMatch against the mapping without leading-zero mismatches
_cat · _famCategory and family stored on importAvoid a mapping lookup on every click
_import_idThe row's source batchUndo exactly one import
05 · Backend and imports

Five steps between the file and an updated dashboard.

The backend is Node.js with Express: 49 routes for the dashboard, imports, user management and history. Raw data imports always follow the same sequence:

The browser reads the file and sends it in batches

large files don't hit the request timeout

The server reads and normalizes each row

values, spelled-out month names, dates and GTINs

It classifies using the in-memory mapping

the GTIN → category and family map is loaded once per import

It writes to Mongo with the prepared fields

each row tagged with its batch

It logs the batch and clears the cache

and prewarms the main queries before the first click

Append or replace

By default, an import appends to the history. In replace mode, the months in the file overwrite the data for the same period, so a corrected month can be re-sent.

Safe undo

Undo deletes the batch's rows (or the entire mapping), removes the log and clears the cache. Clearing the entire history requires the primary user's password.

06 · Performance

The secret is in the input, not the screen.

As the history grew every month, the dashboard started to slow down and some broad queries hit the server's time limit. Each bottleneck became an architecture change:

BeforeCategory and family looked up in the mapping on every query.
→
AfterStored on import (_cat, _fam). The query only groups.
BeforeChanging the mapping meant reprocessing everything on the application server.
→
AfterReclassification with $lookup + $merge inside MongoDB itself, with a progress bar.
BeforeEach tab recalculated on open, and the first visit was slow.
→
AfterIn-memory cache on the dashboard routes and prewarming of the main queries after every import.
BeforeQuerying the full history timed out (504 error).
→
AfterHeavy tabs open on the current year and load on demand, and the broad aggregation was rewritten to stay under the limit.
BeforeDatabase checks and migrations held up the server at startup.
→
AfterStartup doesn't wait for the database: heavy tasks were moved out of startup and the dashboard responds right after deploy.

If the dashboard has to work out category, date or value while displaying, it gets slow. The heavy lifting happens only once, on the way in.

07 · Front end

Seven tabs, the same filters in all of them.

The interface is plain HTML, CSS and JavaScript, with no framework. The filters (year, month, period, store, category, family and product, with multi-select) are standardized across tabs, and every tab exports to Excel and PDF.

08 · Timeline

215 versions in four months.

The dashboard evolved in production, through small and frequent releases. The milestones, taken from the repository history:

  1. Apr 29Initial structureProject with MongoDB and the first dashboard with mappings.
  2. May 06First deployDocker, deployment on Koyeb, import control and history, optimized routes.
  3. May 15Classification in the databaseFilters fed directly from Mongo and mapping reclassification with $lookup + $merge, with a progress bar.
  4. May 18–19Inventory and securityDaily inventory history, password-protected cleanup, XLSX templates and replace mode.
  5. May 26–29ConsistencyCache invalidated on undo, filters standardized across tabs, and multi-select.
  6. Jul 16Product filterA new level of detail in every tab.
  7. Jul 22–31ScaleBatch import of XLS and XLSX, non-blocking startup, no more timeout on the broad aggregation, and GTINs preserved.
  8. Aug 21Public demoStatic version with a mock API in the browser, for the portfolio.

The same technical foundation gave rise to two other dashboards, each with its client's specifics: the Atlas Dashboard (intermediate GTIN mapping) and the Bella Dashboard (manual inventory counts).
